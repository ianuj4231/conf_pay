RAW MYSQL ACCOUNT TRANSACTION API DESIGN

1. Scope

This service implements the required account and transaction behavior from qn.txt.
It uses Node.js, Express, mysql2, and handwritten SQL. It does not use an ORM.

2. Database schema

accounts
--------
- id: BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
- name: VARCHAR(255) NOT NULL
- balance: DECIMAL(19,4) NOT NULL DEFAULT 0.0000
- created_at: DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
- updated_at: DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6)

transactions
------------
- id: BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
- account_id: BIGINT UNSIGNED NOT NULL
- type: ENUM('credit', 'debit') NOT NULL
- amount: DECIMAL(19,4) NOT NULL
- description: VARCHAR(1000) NULL
- reference_id: VARCHAR(255) NOT NULL
- created_at: DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)

Constraints and indexes:
- transactions.account_id references accounts.id.
- amount must be greater than zero.
- UNIQUE(account_id, reference_id) prevents a transaction retry from being applied twice.
- INDEX(account_id, created_at DESC, id DESC) supports unfiltered history.
- INDEX(account_id, type, created_at DESC, id DESC) supports filtered history.
- The id column is the backend-generated transaction ID.
- reference_id is generated by the client and must be reused when retrying the same request.

3. Why reference_id is required

The client creates a unique reference_id before sending a transaction, for example PAY-1001.
The backend creates the database transaction id after insertion. If the network fails after
the database commits but before the response reaches the client, the client retries PAY-1001.
The unique account_id/reference_id constraint finds the original transaction and prevents a
second balance change. The same reference_id is valid for a different account.

4. Create transaction flow

POST /accounts/:accountId/transactions performs these steps:

1. Validate accountId, type, amount, and reference_id before starting database work.
2. Acquire a pooled MySQL connection.
3. START TRANSACTION.
4. Look up account_id + reference_id. If it exists, ROLLBACK and return the existing
   transaction with a duplicate response. Do not update the balance.
5. Lock the account row with SELECT id, balance FROM accounts WHERE id = ? FOR UPDATE.
6. If no account row exists, ROLLBACK and return account-not-found.
7. For debit, reject and ROLLBACK when balance is less than amount.
8. Compute the new balance: balance + amount for credit, balance - amount for debit.
9. UPDATE accounts SET balance = ?, updated_at = CURRENT_TIMESTAMP(6) WHERE id = ?.
10. INSERT the transaction row.
11. COMMIT.
12. Return the inserted transaction and new balance.
13. Any unexpected error executes ROLLBACK and returns an error response.

SELECT ... FOR UPDATE is used because balance-changing requests must serialize on the same
account row. Without the lock, two concurrent debits could both read the same old balance.

5. Atomicity and immutability

The balance update and transaction insert are inside one database transaction. Either both
are committed or both are rolled back. Rejected transactions are not inserted. There are no
transaction update or delete routes, so stored transaction fields remain immutable through
the API.

6. Transaction history

History is ordered by created_at DESC, id DESC. The id tie-breaker makes ordering stable when
two transactions have the same timestamp. page starts at 1 and limit defaults to 20, with a
maximum of 100. The count query and data query use the same account/type filter.

7. Error behavior

- 400: invalid body, type, amount, reference_id, page, or limit
- 404: account does not exist
- 409: duplicate reference_id or insufficient balance
- 500: unexpected database/server error

8. Optional money transfer flow

POST /transfers moves money from one account to another. The request must include a client
generated reference_id. The service first checks the transfers table for that reference_id,
then starts a transaction and locks both account rows with SELECT ... FOR UPDATE. It always
locks the lower account ID first, preventing two opposite-direction transfers from acquiring
the same locks in opposite order. It verifies both accounts exist and the source has enough
balance, updates both balances, inserts one transfer row and two transaction rows, and commits
everything together. Any failure rolls back both balance changes and all inserted records.

9. Startup behavior

When the server starts, it creates the configured database if it does not exist and runs the
schema.sql CREATE TABLE IF NOT EXISTS statements. Therefore, after npm install and .env
configuration, npm start is enough to start the service. schema.sql remains available for
manual database setup.
